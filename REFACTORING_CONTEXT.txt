КРИТИЧЕСКОЕ ПРАВИЛО ПО API ПРОВАЙДЕРОВ
---------------------------------------
Система provider/API уже несколько раз ломалась в предыдущих итерациях.
Были проблемы с POST /api/providers, редактированием существующих API и
добавлением API под другим именем. Из-за этого изменения provider/API были

НЕ МЕНЯТЬ ПОВЕДЕНИЕ provider/API в рамках обычного рефакторинга.

К provider/API относятся как минимум:
- GET /api/providers

- POST /api/providers
- PATCH /api/providers/<pid>

  add_provider(), edit_provider(), del_provider()

HTTP-методы, поля JSON, коды ошибок и рабочий сценарий нужно сохранить.
Любое изменение поведения provider/API считать отдельной задачей и сначала
зафиксировать тестами.

1. ЧТО ПРЕДСТАВЛЯЕТ СОБОЙ ПРОЕКТ
--------------------------------
inhCHAT это локальный веб-клиент для LLM.

Основная схема:

Browser
  -> static/index.html
  -> static/app.js
  -> HTTP
  -> Flask
  -> SQLite / файловое хранилище
  -> OpenAI-compatible provider
  -> при необходимости FreeDeepseekAPI на 127.0.0.1:9655

Основной сервер реально запускается через:
  run_server.py
    -> import server
    -> import work_routes
    -> import work_recovery
    -> подмена server.llm на resilient_llm
    -> Flask app.run()

Главный backend:
  server.py

Work Mode:
  workmode.py
  work_routes.py
  work_recovery.py
  llm_retry.py

Frontend:
  static/index.html
  static/app.js
  static/style.css

Старый/дублирующий backend:
  app.py

Инфраструктура запуска:
  setup.sh
  start.sh
  requirements.txt

2. ВАЖНЫЙ ФАКТ: app.py И server.py
-----------------------------------
В репозитории одновременно существуют app.py и server.py.

server.py является актуальным backend, потому что run_server.py импортирует:
  from server import app, llm as base_llm

app.py содержит старую самостоятельную реализацию Flask-приложения и
частично пересекающуюся бизнес-логику. Это один из главных источников
архитектурного долга.

README также местами описывает структуру через app.py, хотя фактически
запускается server.py.

Рекомендация:
- сначала определить app.py как legacy/dead code;
- проверить grep/import'ы и отсутствие реальных ссылок на него;
- после подтверждения удалить app.py либо вынести его в отдельный legacy
  документ/коммит;
- не делать это одновременно с большим изменением server.py.

Нельзя просто удалить app.py вслепую. Сначала проверить:
  grep -R "from app|import app" .
  grep -R "app.py" .
и документацию/скрипты.

run_server.py оборачивает эту функцию в with_retries(... attempts=3).

Проблемы:
1. JSON хранится прямо в SQLite TEXT:
   chats.messages
   work_runs.source_files
   work_runs.plan
   work_runs.results

2. Нет нормальной миграционной системы. Схема создаётся прямо при импорте
   server.py/work_routes.py, а недостающие поля добавляются через ALTER TABLE.

3. work_events создаётся из work_routes.py, а не централизованно.

4. Нет FOREIGN KEY/CASCADE на уровне SQLite. Удаление связанных записей
   делается вручную.

5. SQLite connections создаются функцией db() без явной настройки:
   - timeout;
   - WAL;
   - foreign_keys;
   - busy_timeout.

При параллельных запросах Work Mode это может стать проблемой.

6. save_chat в server.py и save_chat в work_routes.py дублируют друг друга.

7. work_runs привязан к chat_id, но выбор активного run делается через:
   ORDER BY created_at DESC LIMIT 1.
   При параллельных запусках это потенциально неоднозначно.

Рекомендация:
создать отдельный db.py/database.py с:
- get_connection()
- transaction helper
- migrations
- repository functions
- единым включением PRAGMA foreign_keys=ON
- WAL/busy timeout, если это подтверждено тестами как безопасное для
  текущего сценария.

Не переписывать схему сразу. Сначала покрыть текущие сценарии тестами.

8. USERS И AUTH
---------------
users.json является источником истины для списка пользователей.

При старте:
- users() читает users.json;
- sync() хэширует пароль через PBKDF2 SHA-256 600000;
- затем создаёт/обновляет запись в SQLite.

Это работает, но архитектурно странно:
- пароль хранится в открытом виде в users.json;
- при каждом запуске хэш создаётся заново;
- SQLite становится производным хранилищем пользователей.

auth decorator:
- проверяет session['uid'];
- снова читает users.json;
- проверяет существование пользователя в SQLite;
- проверяет, что email присутствует в активном users.json.

Плюс:
удаление пользователя из users.json инвалидирует его дальнейшие защищённые
запросы.

Минусы:
- чтение users.json на каждый auth request;
- смешение конфигурации пользователей и БД;
- секрет сессии имеет небезопасный fallback:
  change-me-in-.env

Для локального приложения это приемлемее, чем для публичного сервера, но
при рефакторинге нужно явно сохранить границу: проект рассчитан на локальный
Mac, а не на публичный production deployment.

10. ОБЫЧНЫЕ ЧАТЫ
----------------
Обычный запрос:
POST /api/chats/<cid>/message

Поток:
1. Проверяется chat.
2. Берётся provider_id из формы или из chat.provider_id.
3. Проверяется provider принадлежностью текущему user_id.
4. При наличии файлов вызывается ingest_uploads().
5. Загружается последние 20 user/assistant сообщений.
6. Формируется system prompt.
7. Добавляется shared library context.
8. Если meta_analysis включён, добавляется контекст других чатов.
9. Добавляются source files.
10. Добавляется user content.
11. вызывается llm().
12. результат записывается в chats.messages.

Проблема контекста:
обычный чат имеет жёсткий срез history[-20].
При длинных сообщениях фактический prompt может стать очень большим.

Проблема архитектуры:
формирование prompt происходит прямо внутри route.

Рекомендация:
выделить:
- ChatRepository
- ContextBuilder
- LLMClient
- ChatService

Но внешний endpoint оставить прежним.

11. META-ANALYSIS
-----------------
Идея:
обычный чат изолирован.
При включении toggle meta_analysis разрешается использовать контекст других
не-временных чатов текущего пользователя.

server.py:
meta_chat_context(current_cid)

work_routes.py:
meta_chat_context()

Контекст:
- до 20 других чатов;
- последние 6 сообщений каждого;
- максимум 12000 символов на чат;
- общий максимум 250000.

Это хорошая базовая модель изоляции, но реализация дублируется.

Рекомендация:
одна функция/сервис:
build_cross_chat_context(user_id, current_chat_id)

Нельзя сделать meta-analysis глобально включённым по умолчанию.
Переключатель является частью продукта.

13. SHARED LIBRARY
------------------
Общая библиотека:
workspace/library/<user_id>/

Файлы доступны всем чатам одного аккаунта.

server.py:
- GET /api/library
- POST /api/library
- DELETE /api/library/<path>
- GET /api/library/file/<path>

Контекст для LLM:
library_text()

work_routes.py имеет собственную:
shared_library_context()

Это дублирование.

Ограничение контекста:
server.py library_text() -> 800000 символов.
work_routes.py shared_library_context() -> 800000.

Проблемы:
- при загрузке файл сохраняется по basename;
- два файла с одинаковым именем перезаписывают друг друга;
- библиотека не имеет каталогов через UI;
- нет checksum/versioning;
- все текстовые файлы перечитываются при каждом запросе;
- бинарные файлы хранятся, но в LLM context не попадают.

Рефакторинг:
LibraryService + FileStorage abstraction.

Не менять публичный URL API без необходимости.

14. WORK MODE: ИДЕЯ
-------------------
Work Mode превращает один пользовательский запрос в:

INTAKE
  -> PLAN
  -> TASK 1
  -> TASK 2
  -> ...
  -> FINAL

Каждый Work run имеет iteration.

Структура:
workspace/chats/<chat_id>/iterations/<N>/

Итерации позволяют:
- хранить отдельные результаты;
- читать предыдущие итерации;
- копировать файлы из старой итерации;
- выбирать вложения из старой итерации;
- повторно продолжать незавершённую работу.

Это одна из главных продуктовых идей проекта.

15. workmode.py
---------------
Основные константы:
TEXT_EXT
MAX_UPLOAD = 24 MB
MAX_FILES = 200
MAX_FILE_TEXT = 150000
MAX_CONTEXT = 2000000
MAX_ARCHIVE_FILES = 200
MAX_ARCHIVE_SIZE = 64 MB

safe_child(root, rel):
защищает от выхода за root через resolve().

text_from(path):
читает только поддерживаемые текстовые расширения;
берёт до MAX_FILE_TEXT*4 байт;
не обрабатывает первые 4096 байт с NUL как текст;
decode utf-8 errors=replace;
обрезает до MAX_FILE_TEXT.

ingest_uploads():
- сохраняет upload;
- для ZIP распаковывает;
- ограничивает число файлов;
- ограничивает размер текстовых элементов;
- извлекает текст.

parse_plan():
- пытается найти JSON array в ответе LLM;
- fallback: разбивает строки ответа на задачи;
- максимум 12 задач.

create_archive():
- проверяет пути;
- максимум 200 файлов;
- максимум 64 MB исходных файлов;
- ZIP_DEFLATED.

Риск:
parse_plan() слишком permissive. Он принимает fallback почти любой текст как
план. Для стабильного Work Mode лучше перейти к строгой JSON schema/валидатору,
но только в отдельной задаче после фиксации текущего поведения.

17. WORK MODE DIRECTIVES
------------------------
LLM может выдавать специальные инструкции:

path

Эти directives являются фактически внутренним protocol между LLM и backend.

Это очень важная часть архитектуры.

Нельзя при рефакторинге заменить их случайно обычным Markdown parsing.
Лучше рассматривать их как protocol layer.

Рекомендация:

work_protocol.py

с typed representation:
FileArtifact
CopyOperation
ArchiveRequest
GitHubCloneRequest
AttachmentRequest

18. MATERIALIZE_TASK
--------------------
materialize_task() реально изменяет файловую систему по ответу модели.

Он:
- создаёт FILE;
- clone public GitHub;
- копирует COPY_FROM;
- создаёт ARCHIVE.

Важный принцип безопасности:
все пути проходят safe_file/safe_child.

GitHub разрешён только:
https://github.com/...

и clone:
git clone --depth 1

Проблемы:
- ошибки materialization часто silently swallowed;
- LLM может выдать некорректный directive и пользователь не увидит точную
  причину;
- GitHub clone может занимать до 180 секунд;
- нет cancellation;
- нет ограничения общего размера клонированного репозитория;
- clone запускается subprocess;
- нет проверки содержимого после clone;
- директория может уже существовать;
- отсутствует явная модель состояния операции.

Рефакторинг:
отдельный ArtifactService/WorkspaceService и явный результат:
  created / skipped / failed + reason.

Но не менять протокол без тестов.

- либо отдельный sequence;

20. WORK PLAN
-------------
POST /api/work/plan/<cid>

Планировочный LLM получает:
- original request;
- shared library;
- cross-chat context, если meta_analysis;
- current + previous iteration files.

Затем parse_plan().

КРИТИЧЕСКАЯ ПРОБЛЕМА:
work_runs не содержит meta_analysis.

В plan():
meta = bool(r['meta_analysis']) if 'meta_analysis' in r.keys() else False

В task() и final() используется та же проверка.

Поскольку meta_analysis находится в chats, а не work_runs, условие фактически
не получает настройку из chat и обычно даёт False.

Следовательно, UI toggle meta-analysis и Work Mode сейчас логически не
связаны корректно.

Это надо исправить отдельной функциональной задачей, не маскировать во время
рефакторинга.

Правильная архитектурная модель:
при старте run зафиксировать snapshot настроек чата:
- provider_id;
- meta_analysis;
- возможно model/config.

Тогда run воспроизводим, даже если пользователь потом переключит настройки.

21. WORK TASK
-------------
POST /api/work/task/<cid>

Получает:
- provider_id;
- task index.

Берёт latest run.

Дальше:
- tasks из JSON;
- results из JSON;
- source;
- available files;
- previous task results.

LLM получает system instruction:
execute ONLY assigned task.

После ответа:
materialize_task()
results update
task_done event

Критическая проблема идемпотентности:
результат задачи считается завершённым после одного запроса.
Если frontend повторит POST из-за timeout/retry, задача может быть выполнена
второй раз.

Особенно опасно для:
- FILE;
- COPY_FROM;
- ARCHIVE;
- GITHUB clone.

Нужен позже task-level idempotency key/state.

Также run/results не имеют отдельной таблицы work_tasks.
Сейчас индекс задачи хранится внутри JSON results.

Для рефакторинга это один из основных кандидатов на нормализацию.

22. WORK FINAL
--------------
POST /api/work/final/<cid>

LLM получает:
- request;
- shared library;
- meta context;
- available files;
- source files;
- completed task results.

LLM выбирает вложения через:
[[ATTACH: path]]

Backend валидирует пути через safe_file() и возвращает file cards.

Это хорошая идея: финальная модель сама выбирает релевантные артефакты.

Но final сейчас не проверяет, что ВСЕ плановые задачи выполнены.
Это частично контролируется frontend/continue flow, но backend endpoint сам
по себе может быть вызван раньше.

Для надёжности final должен проверять run state на сервере.

23. RECOVERY / CONTINUE
-----------------------
GET /api/work/continue/<cid>:
- latest run;
- plan;
- results;
- done indexes;
- missing indexes;
- can_finalize.

POST /api/work/continue/<cid> фактически просто вызывает GET:
def work_continue_post(cid):
    return work_continue(cid)

Это не настоящая state transition.

Frontend:
- после ошибки показывает кнопку Продолжить;
- получает next_index;
- выполняет оставшиеся задачи.

Плюс:
ранее завершённые задачи не запускаются заново.

Минусы:
- состояние inferred из results JSON;
- нет explicit task status;
- нет started_at/finished_at/error/retry_count;
- нет lock;
- latest run может быть не тем run при конкуренции.

24. EVENT STREAM
----------------
work_events используется для UI polling.

Frontend опрашивает:
GET /api/work/status/<cid>?after=<lastEvent>

Период:
700 ms.

Backend возвращает максимум 100 событий.

Frontend хранит lastEvent только в памяти.

Проблемы:
- polling вместо SSE/WebSocket;
- если вкладка была закрыта, состояние восстанавливается через continue,
  но события могут быть потеряны;
- run_status inferred from final_answer;
- нет explicit event cursor semantics per client;
- work_status выбирает latest run.

Для локального приложения polling приемлем. Не переписывать на WebSocket без
необходимости. Сначала улучшить state model.

25. RETRY
---------
llm_retry.py содержит retry wrapper, который подключается только через
run_server.py:

server.llm = resilient_llm
work_routes.llm = resilient_llm

Это monkey patch.

Проблема:
поведение приложения зависит от точки входа. Если кто-то запускает server.py
напрямую или импортирует app иначе, retry может отсутствовать.

Рефакторинг:
создать LLMClient/ResilientLLM, который сам является dependency.

Не оставлять скрытый monkey patch как конечную архитектуру.

26. run_server.py
-----------------
Сейчас это dependency injection через mutation:

import server
import work_routes
import work_recovery

server.llm = resilient_llm
work_routes.llm = resilient_llm

Это работает, но хрупко.

Кроме того, work_routes imports llm from server:
from server import ..., llm, ...

После импорта name llm в work_routes является объектом функции, поэтому
server.llm = resilient_llm отдельно подменяет server.llm, а
work_routes.llm подменяется вручную.

Это сильный сигнал, что нужен нормальный service dependency.

36. start.sh
------------
Текущий start.sh:
- активирует .venv;
- проверяет FreeDeepseekAPI;
- проверяет users.json;
- запускает DeepSeek proxy, если есть deepseek-auth.json;
- запускает python run_server.py;
- cleanup через trap.

В текущем Git tree start.sh имеет mode 100644, а не executable 100755.

Поэтому на локальном Mac было:
zsh: permission denied: ./start.sh

Решение локально:
chmod +x start.sh setup.sh

Но chmod локально не гарантирует, что executable bit попадёт в GitHub.
Если это надо исправлять в проекте, отдельной задачей сделать Git mode 100755
для обоих shell scripts.

README ожидает:
chmod +x setup.sh start.sh
поэтому документация уже компенсирует проблему.

39. БЕЗОПАСНОСТЬ: PATH TRAVERSAL
-------------------------------
Есть хорошая базовая защита:
safe_child()
safe_file()
resolve()
проверка root in p.parents.

Это сохранять.

Но необходимо отдельно проверить:

- symlink handling;
- duplicate ZIP entries;
- hard links/symlinks после Git clone;
- archive output paths;
- race between validation and file operation.

Особенно нельзя считать ZIP безопасным только потому, что имя прошло
safe_child(). Архивы являются отдельным trust boundary.

40. БЕЗОПАСНОСТЬ: GITHUB

без отдельной sandbox architecture.

42. FILE UPLOADS
---------------
MAX_CONTENT_LENGTH = 32 MB.
ingest_uploads отдельный лимит = 24 MB на файл.

Это означает:
- один файл максимум 24 MB;
- общий HTTP request максимум 32 MB.

MAX_FILES для ZIP = 200.

Но число обычных multipart файлов отдельно не ограничено явным MAX_FILES.
Это стоит добавить позже, если потребуется.

43. КОНТЕКСТ LLM
---------------
Самая большая потенциальная производительность проблема проекта:
контекст файлов формируется повторным чтением файлов с диска и склеиванием
огромных строк на каждый LLM request.

Work Mode может передавать до ~2 MB source context.
Library до ~800k.
Meta до ~250k.
Плюс task results.

Это может легко выйти за context window некоторых моделей.

Нужна отдельная ContextBudget/ContextBuilder архитектура:
- token/char budget;
- приоритеты;
- deduplication;
- truncation policy;
- file summaries;
- selected files instead of everything.

Не решать это простым увеличением лимитов.

44. ИЗОЛЯЦИЯ ЧАТОВ
------------------
По умолчанию обычный chat history берётся только по chat_id.

Work Mode task context:
current iteration + previous iterations этого же chat.

Cross-chat context должен появляться только при meta_analysis.

Shared library является отдельным глобальным для аккаунта контекстом и
доступна всем чатам.

Это три разные области данных:

A. Current chat:
   обычная история + текущие файлы.

B. Same-chat Work history:
   iterations.

C. Account-wide:
   library.

D. Other chats:
   только meta_analysis.

Не смешивать эти области в один generic context list без source type.

45. ПРОБЛЕМА SNAPSHOT НАСТРОЕК
------------------------------
Work run сейчас не сохраняет provider/meta configuration как полноценный
snapshot.

Если пользователь изменит provider/meta toggle во время незавершённого run,
часть запросов может работать с текущим frontend provider, а часть
с сохранённым run context.

Для воспроизводимости run должен иметь:
- provider_id snapshot;
- model snapshot;
- base_url snapshot или provider version;
- meta_analysis snapshot;
- возможно system prompt version.

Но provider/API нельзя ломать ради этого. Лучше добавить поля в work_runs
или отдельную run_config таблицу.

58. ОСНОВНАЯ ТЕХНИЧЕСКАЯ ИДЕЯ ПРОЕКТА
--------------------------------------
Самая важная часть inhCHAT не обычный LLM chat. Это Work Mode как локальная
agent-like orchestration система с файловым workspace.

Её ключевые свойства:

- один запрос пользователя превращается в plan;
- plan разбивается на независимые задачи;
- каждая задача получает контекст;
- результаты сохраняются;
- файлы являются first-class artifacts;
- iterations сохраняют историю рабочих результатов;
- предыдущие iterations доступны только внутри текущего chat;
- shared library отдельно доступна всему аккаунту;
- cross-chat context разрешается отдельным meta-analysis toggle;
- после сбоя можно продолжить с первой незавершённой задачи;
- final model выбирает, какие artifacts реально приложить.

При рефакторинге именно эти инварианты должны считаться ядром продукта.

59. КРИТИЧЕСКИЕ ПРОБЛЕМЫ В ПОРЯДКЕ ВАЖНОСТИ
--------------------------------------------
1. Отсутствие полноценного тестового набора.
2. Provider/API исторически нестабилен, поэтому его нужно сначала заморозить
   тестами.
3. Work Mode state хранится частично в JSON и определяется косвенно.
4. Нет task-level idempotency и явной state machine.
5. run_row() выбирает latest run, что плохо для concurrency.
6. Work run не имеет полноценного snapshot настроек.
7. meta_analysis не переносится корректно в work_runs.
8. server.py и work_routes.py перегружены ответственностями.
9. app.py выглядит как legacy duplicate.
10. app.js перегружен глобальным состоянием и UI/API logic.
11. Context generation может создавать огромные prompts.
12. SQLite setup/migrations распределены по модулям.
13. File/ZIP/GitHub operations требуют дополнительного hardening.
14. API keys хранятся plaintext в SQLite.
15. start.sh/setup.sh не имеют executable bit в Git tree.
16. README частично описывает старую архитектуру.

63. ФИНАЛЬНОЕ ПРЕДУПРЕЖДЕНИЕ
----------------------------
Главная опасность этого проекта сейчас не в количестве кода, а в том, что
несколько разных подсистем уже работают, но их состояние распределено между
SQLite, JSON, файловой системой, Flask session и JavaScript globals.

Поэтому "рефакторинг" здесь должен означать постепенное наведение границ
между подсистемами с сохранением поведения.

Особенно:
- provider/API не трогать без regression tests;
- Work Mode не упрощать до обычного chat request;
- iterations не превращать в одну общую папку;
- meta-analysis не делать глобальным контекстом;
- temporary не считать просто UI-флагом;
- artifacts не считать обычным текстом ответа модели;
- directives считать внутренним protocol;
- frontend race protection viewToken сохранить;
- path safety сохранить и усилить.

Это состояние проекта на commit 90157d5. Любая следующая итерация должна
сначала свериться с фактическим кодом, потому что этот файл является
контекстом для рефакторинга, а не заменой исходникам.

ПОСЛЕДУЮЩАЯ ИТЕРАЦИЯ: STRICT REPORT GENERATION (2026-09-18)

Цель
-----
Work Mode теперь умеет принимать методички и примеры в DOCX/PDF и, при включенной пользовательской настройке «Строгое форматирование», собирать готовый учебный отчет сразу в двух форматах: DOCX и PDF.

Источник требований
-------------------
В качестве базового профиля форматирования используется структура и правила из предоставленных материалов:
- титульный лист;
- цель/задачи;
- пошаговое выполнение;
- места для скриншотов/рисунков;
- ответы на контрольные вопросы;
- итоговый вывод;
- Times New Roman, 14 pt, черный цвет;
- выравнивание по ширине;
- межстрочный интервал 1,5;
- первая строка 1,25 см;
- поля: 3,0 / 1,5 / 2,0 / 2,0 см;
- нумерация страниц снизу по центру, титульный лист считается, но номер на нем не отображается;
- заголовки полужирные, без точки;
- перед рисунком должна быть ссылка, под ним полная подпись «Рисунок N - ...» без сокращения «Рис.» и без точки в конце.

Архитектура
-----------
report_builder.py отвечает за:
1. извлечение текста из DOCX/PDF;
2. очистку и разбор JSON-спецификации отчета, которую возвращает модель;
3. строгую нормализацию метаданных;
4. генерацию DOCX;
5. генерацию PDF;
6. создание явных плейсхолдеров для отсутствующих изображений.

Work Mode не просит модель «рисовать» документ HTML/Word-разметкой. Модель формирует содержательную JSON-спецификацию, а детерминированный backend сам применяет форматирование. Это существенно снижает вероятность того, что модель сломает поля, шрифты, номера страниц или структуру документа.

Ограничение достоверности
-------------------------
Модель запрещена от выдумывания измерений, результатов выполнения, скриншотов и иных фактов. Если в исходных материалах требуется рисунок, а изображения пользователя отсутствуют, backend создает место вида «[ МЕСТО ДЛЯ РИСУНКА N ]» и корректную подпись.

Платформенная адаптация
-----------------------
Пользовательские условия являются частью запроса Work Mode. Например, если методичка рассчитана на Windows, а пользователь просит выполнить вариант для macOS, модель должна адаптировать инструкции к macOS, но не должна утверждать, что команда реально выполнена, если подтверждающего результата нет.

Настройка
---------
Флаг «Строгое форматирование» хранится в localStorage интерфейса и передается в /api/work/intake. Для каждой рабочей итерации значение также сохраняется в work_runs.strict_formatting. Поэтому обычный Work Mode не начинает неожиданно генерировать документы.

Зависимости
-----------
Добавлены python-docx, pypdf и reportlab.

Известное ограничение текущей реализации
-----------------------------------------
DOTX-шаблон пока не используется как бинарный шаблон Word. Поддерживается чтение DOCX/PDF как источников и детерминированная генерация DOCX/PDF по профилю форматирования. Это сделано намеренно, чтобы сначала получить устойчивый общий pipeline; перенос стилей/колонтитулов из конкретного DOTX можно сделать отдельным этапом.

Тестирование
------------
Локально обязательно выполнить:
python -m unittest discover -s tests -v
python -m py_compile server.py provider_service.py workmode.py work_routes.py work_recovery.py llm_retry.py run_server.py report_builder.py

После установки зависимостей проверить вручную:
1. обычный Work Mode без строгого форматирования;
2. Work Mode с DOCX методичкой;
3. Work Mode с PDF методичкой;
4. строгий режим с дополнительным условием «выполнить под macOS вместо Windows»;
5. наличие двух вложений DOCX/PDF;
6. наличие плейсхолдеров рисунков;
7. корректность полей, шрифта, интервала и нумерации.
